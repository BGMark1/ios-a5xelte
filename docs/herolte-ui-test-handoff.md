# HEROLTE UI test handoff

The test device is a Galaxy S7 SM-G930F running the HEROLTE port. The current control image presents a 1242 × 2208 iOS canvas, enables the audio driver, and requests 1976 MHz on the Mongoose cores and 546 MHz on the Mali GPU. The recovered boot log confirms both clock settings. SpringBoard logged the icon width change from 56 to 60.48 points. The captures confirm that the red diagnostic status bar still appears on the home screen.

The SpringBoard wrapper source is `tools/ios/herolte-home-ui.c`. The compiled wrapper in the workspace is `s7-setup/libhomeui-test.dylib`. The drop package installs it as `lib/libherosb.dylib` and keeps the original wallpaper library as `lib/libherosb-base.dylib`. It also carries the audio installer and original Samsung wifi firmware and NVRAM. The timed screenshot test reuses that package. The control boot and drop package together are the rollback baseline for this round.

The test patch `xnu/patches/0322-herolte-panel-capture.patch` samples the actual BGRA panel buffer as 480 × 853 RGB565. With `herotwrp=120 herocap=1 herohome=1`, the existing recovery thread sends one Home press, captures the panel four seconds later, and returns to TWRP after allowing the existing log flush to run. Capture and input are opt-in test flags. A Home event can wake a locked phone. The result may therefore be the lock screen.

The [private XNU build](https://github.com/BGMark1/galaxy-s7-ios-private-build/actions/runs/42327839616) uses branch `codex/herolte-ui-probe` and commit `770aa382999cb2ad377713334a559094eab61297`. Download the `xnu-kernel-macos-15-intel` artifact and check `SHA256SUMS`. Pack the resulting `kernel.development.herolte` with the current 8 Plus ADT and the control image's boot arguments plus the three test flags. The control image in the local workspace is `s7-setup/audio-ui-clock-test.img`, SHA-256 `48b48be84cd3ff26f70bbcf5bbd54189de956a1bb670f9aad30ade8258319a68`.

With the S7 in TWRP, run:

```text
python tools/herolte-ui-test.py ADB SERIAL TEST.img CONTROL.img NEW_OUTPUT_DIRECTORY
```

The runner checks the model, recovery, BOOT partition and control image hash. It verifies the written test image, waits for a new recovery session, extracts a fresh log and decodes the PNG. It then restores and verifies the control BOOT and leaves the phone in recovery. If recovery never returns, the hardware buttons are required to enter TWRP before restoring the control BOOT. The runner writes only BOOT from TWRP. The kernel sends capture data through the already installed persistent log.

The host decoder has been checked with known RGB565 colors, a full-size synthetic capture and a truncated capture. A successful device trial requires an actual image, a new boot log containing the Home marker, and a verified return to TWRP. Keep screenshots and device logs out of the repository. Future tap and swipe tests can reuse the touch driver event path once the first timed Home and capture trial is verified.

The first device run produced a complete PNG showing the home screen, including the red diagnostic bar. XNU logged the Home key down and up with one HID client and reached the timed recovery path. ADB detected TWRP shortly after the original host timeout, so the runner now allows 150 seconds beyond the in-kernel timer. The SpringBoard diagnostic scan had also ended before the Home key event. The next run extends it to 90 checks at two-second intervals.

The second run completed end to end. The runner booted the probe, observed the return to TWRP, extracted a fresh PNG and restored the verified control BOOT. The updated diagnostic scan still did not hide the red bar in the captured home screen. Inspect which process owns the diagnostic view before changing status bar behavior again. The test kernel SHA-256 is `82bd87d8c531aea421c90257c542e48b26546572430411af4c37e053ceb24d2f`. The local test artifacts are under `s7-setup/xnu-ui-probe-42327839616/device-test-2`.

The control boot peaked at 59.3 displayed frames/s over a five-second log interval. Its median reported frame copy time was 4.37 ms. The first unattended boot's median was 4.30 ms, with different screen activity. A matched swipe test is still needed to compare UI smoothness.

Patch `0323-herolte-repeatable-swipe-test.patch` adds 12 alternating horizontal swipes to the Home probe when `heroswipe=1`. The host reporter `tools/herolte-swipe-report.py` compares full framebuffer reporting intervals inside the gesture window. Its displayed FPS includes the fixed pause between gestures. The [private swipe build](https://github.com/BGMark1/galaxy-s7-ios-private-build/actions/runs/42355796750) is used for two boots with the same iOS data and input sequence. The only planned boot argument difference is the Mongoose and Mali clock override. Compare the resulting screenshots and logs before adopting a clock setting.

The optional `status.trace` drop file asks the SpringBoard wrapper to log a bounded inventory of window and status bar classes at two points in the boot. It records class names and provider types only. Use the trace to locate the diagnostic view before attempting to replace or hide it.

The initial trace completed before the automatic Home press. It saw `SBFStatusBarLegibilityView` under both the home and lock screen windows, plus `SBStatusBarReusePoolWindow`, but no UIKit fallback provider. The later capture still showed the red bar. The next trace needs a sample while the bar is visible, after opening Home, to determine its owner.

Both physical swipe runs completed, delivered twelve HID releases, captured Home and restored the control BOOT. Three full intervals per run gave 13.1 fps at the bootloader clock settings and 20.7 fps with Mongoose 1976 MHz and Mali 546 MHz. Median panel copy time was 5.67 ms versus 4.39 ms. The raised-clock run supplied 331 swaps and overwrote 19, compared with 198 and 1 at baseline. The pauses between swipes count in both FPS values. Both captures show the wallpaper and the red bar. The calendar widget was blank in the baseline capture and populated in the second, which could reflect startup timing.

The same swipe kernel and raised clocks were tested with `herogl=1`. The regular EAGL bridge reached 28.6 fps (27.7 in the slowest full interval), with 9 of 441 swaps overwritten and a 4.51 ms median copy. The HakiOS bridge at the same path reached 26.6 fps (25.9 slowest), with 8 of 410 swaps overwritten and a 4.32 ms median copy. Both logs confirm GPU submissions by backboardd. Both captures show the home wallpaper, icons, translucent dock and the red diagnostic bar. The Weather widget has visible color bands in the regular bridge capture. Neither run establishes continuous 60 fps or verifies the lock screen. The raised-clock control without EAGL was 20.7 fps.

The regular bridge was retested with only `HERO_ASYNC=1` in `gl.env`. backboardd logged queued submissions and the run reached 30.3 fps (28.4 slowest), versus 28.6 fps (27.7 slowest) with synchronous submissions. One-tick gaps increased from 36.1% to 42.8%. Overwrites increased from 9/441 to 18/476 and median copy time increased from 4.51 ms to 4.67 ms. The recovered image still shows the wallpaper, translucent dock, icons, red bar and Weather widget bands. This is one paired measurement. The control BOOT was restored and verified. The staged control package now explicitly sets `HERO_ASYNC=0`.

GPU execution accounted for 13–22% of the synchronous swipe windows and 17–25% of the asynchronous windows. The HakiOS frame trace also shows expensive frames and copy spikes. GPU execution time alone does not explain the full frame cost. The next performance pass should profile backboardd or compare the opt-in Mesa mapping cache with the same test and inspect the result for rendering regressions.

A separate backboardd profiling run used `HERO_ASYNC=1 HERO_PROF=1` with the 1242 × 2208 canvas. It reported 34.7 fps, but the sampling changes the workload and successive runs vary. The report printed inside the gesture window contained 1490 samples. 54.4% were in libsystem_kernel, including 45.1% at `mach_msg2_trap`. QuartzCore and libOSMesa accounted for 17.7% and 12.8%. A sampled syscall position does not establish where the critical path stalls. No single named Mesa function exceeded 1% in that report.

The same async EAGL build at 750 × 1334 reached 36.9 fps and 2.82 ms median panel copy time. The 750 ADT differs from the control in the canvas dimensions, display scale and artwork scale/subtype, aside from its random seed. The capture shows the red bar, overlapping icons and a clipped dock. SpringBoard reported 60.48 pt icon width, and the captured icons are about 116 pixels wide at 480-pixel panel preview width. That matches `60.48 × 3 × 480 / 750`, consistent with a retained 3× UIKit scale despite the ADT's requested 2×. Measure UIScreen scale and MobileGestalt answers on the device before changing the cache or choosing this mode. Both runs restored the verified control BOOT and staged `HERO_ASYNC=0`. Captures and logs are in the local `panfrost-profile` and `panfrost-750` folders under the swipe build.

The opt-in `screen.trace` drop file enables a read-only probe in SpringBoard. In the 1242 × 2208 run, UIKit reported 414 × 736 points, scale and native scale 3. In the 750 × 1334 run it reported approximately 250 × 445 points, also at 3×. Both reported MobileGestalt ArtworkDeviceSubType 2436, which matches the donor iPhone X rather than either candidate ADT. The selected MainScreenScale and ArtworkScaleFactor keys returned no numeric answer. This confirms the mismatch and makes the persistent MobileGestalt cache a testable suspect, without proving it is the only cause. The next experiment should move that specific cache aside with a verified backup, boot the 2× ADT again, then restore the saved cache when returning to the 8 Plus control. The two trace runs completed at 30.9 and 35.8 fps respectively, and the runner verified the control BOOT and staged the original SpringBoard wrapper afterward. Local results are under `screen-trace-panfrost` and `screen-trace-panfrost-750`.

`tools/ios/herolte-mg-cache.c` is a root autorun for the cache experiment. It reads `mg-cache-mode` from the drop zone. `save` renames the one identified cache file to a sibling and verifies its fingerprint and length. Repeated `save` preserves the original backup. `restore` renames it back and verifies it again. The local fixture covered saving, a repeated save after regeneration and restoring the original bytes. The ARM64 build and all three device boots completed.

At 750 × 1334, UIKit switched to 375 × 667 points at 2× and MobileGestalt returned subtype 1334 in both boots. Both captures show the normal clock, Wi-Fi and battery status bar, a full dock, distinct icons, two widgets and the home wallpaper. The second boot preserved the already-saved cache backup and reproduced the result. These runs scored 27.5 and 29.6 fps in the twelve-swipe test, including pauses. The old 35.8–36.9 fps 750p results were on a visibly broken layout and should not be used as the target. The restore boot logged verification of all 8017 original cache bytes, and UIKit reported 414 × 736 at 3× with the original MobileGestalt subtype again. The control BOOT and original drop were verified in recovery. The local result directories are `mg-cache-save`, `mg-cache-fresh` and `mg-cache-restore`. Lock screen wallpaper and sustained 60 fps still need physical verification.

The control log reports eight initialized CPUs and verified interprocessor interrupts. Patch `0238` already prefers the four Mongoose cores for high-priority work through the default mask `0xf0`. The Snapdragon S9 port is a reference for a second, independent experiment. Its CoreAnimation measurements improved when libdispatch reported a parallelism of two for the relevant QoS classes. Compare reproducible scroll tests and interprocessor interrupt rates on the S7 before choosing a default. The S9 also demonstrates an SSH-based workflow, which can inform live control on the S7 after the offline capture test. Its USB controller and panel code are hardware-specific. ## Lock fade trial

On the approved daily BOOT, the user reported visible brightness steps when locking. Its recovered log shows the physical Power press, display off, a later Power press and display on. The framebuffer driver halves each pixel channel on six callbacks and clears to black on the seventh. This repeatedly reads and writes the 1440 × 2560 scanout on the CPU.

The isolated `codex/herolte-lock-fade` branch starts from the approved double-buffer kernel. Local commit `243e6a1` and private head `83116f27f47ca3b80da9ad5f5719714d944956a3` add opt-in lock timing and a one-pass black comparison. Both images keep the same ADT and GPU settings. The timed test sends Home, locks with a short Power press, wakes with a second press and captures the panel. The previous 750p daily BOOT is verified and restored after each run. Existing iOS files and drop package are reused for the test. [Private build 42420409758](https://github.com/BGMark1/galaxy-s7-ios-private-build/actions/runs/42420409758)

The first two boots returned to TWRP and restored the approved BOOT. Both delivered the synthetic Power events, but `a5fb_keep_on` rejected display-off because the test had skipped the timestamp recorded by the physical GPIO Power path. Those boots provide no fade timings. Local commit `e3ba96d` and private head `cd7658aec04c4b82d935b931f59730ff5e0e8833` set the same timestamp immediately before the test press and retain the original keep-on policy. [Corrected build 42421869631](https://github.com/BGMark1/galaxy-s7-ios-private-build/actions/runs/42421869631)

The corrected kernel passed CI and the Cortex-A53 check. Both device logs show display off after the Power press and display on after the wake press. The gradual run has no completion marker before wake, so it provides no full fade time. The one-pass run wrote the black framebuffer in 37.462 ms from display-off, including 21.042 ms in the callback. This is a kernel measurement from the display-off request to completion of writes, before the physical panel has necessarily finished scanning the image. Both wake captures show the full wallpaper, carrier and battery, and Home prompt. Large clock and date are still absent. Local evidence is under `s7-setup/idma-ab/lock-fade-verified`.

The one-pass setting was installed as `approved-750p-fast-lock.img` with the same 750p ADT and double-buffer options. The timed recovery, simulated keys and capture flags were removed. BOOT SHA-256 `3f9c0da15adb57b98c8ae8427a21dadb05e6bce621db0dec3eb1b532e2dbcc74` passed readback. ADB requested normal reboot.
